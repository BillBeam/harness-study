## 一、主循环入口在哪

只有一台循环机器：ReactLoopAgent。它自外向内是四层——`wakeDriver()` 启动 `kick()`，`kick()` 反复调用 `turn()`，`turn()` 里是 step 循环，`step()` 里是单次模型请求的重试循环，最内层是一个 step 内工具调用的分组循环。这台机器由 AgentLoop（AgentFactory 的实现）构造，两条组合都经由 AgentRegistry 的 create/resume 走到同一处。headless 与 Web 的差别不在循环本身，而在「谁往 inbox 投消息、谁等它转完」：headless 在插件 mount 时跑一次性 run()，投一条 followup 后 await whenIdle 然后退出进程；Web 每收到一次浏览器 RPC 就 steer/followup 一次，立即返回 accepted，不等 whenIdle。

## 二、工具调用在哪里被校验和分发

一次工具调用的链路是：step() 从 assistant 消息里 filter 出 tool-call 块 → executeToolCalls 解析参数并按并发模式分组 → 每个调用走 ToolRuntime 的四段调度器 prepare / dispatch / finalize / finish。参数的 schema 校验不在注册表里，而在 defineTool 生成的 execute 包装器里（自写的 JSON Schema 子集校验器）；权限与审批在 prepare 那一环（tools/pre-execute 瀑布 + approval 服务 + guard）；按名查表分发在 dispatchToolBody；返回值再过一次同一个校验器。两条组合的分发与校验代码完全相同，差别有两处：一是审批的应答者（Web 有浏览器端 UI 应答者，headless 没有），二是被查的那张工具表怎么被填（Web 把 host 层的一批工具行 disable，改由每个会话的 agent preset 往自己的 scope 层注册）。

## 三、会话或轨迹被写到哪

轨迹的唯一真源是 Session 的追加式事件日志：Session.append 分配 seq/time、deepFreeze 后 push 进内存 log，并同步派发 session/event。持久化协调器在 session/created / session/event / session/flush / session/disposed 四个点接上写路径：事件先进 write-behind 队列（结构化克隆 + 定时批），落盘时在 appendCore 校验 seq 连续后交给后端。两条组合都用 base 层挂载的 JSONL 后端，根目录为 DSH_HOME 下的 sessions，路径形如 `<root>/--<归一化 cwd>--/<编码后的会话 id>/session.jsonl.zstd`。除会话日志外还有几处旁路落盘：投影缓存、附件对象、spill 文件、遥测上报。差异在于会话怎么被建（headless 每次进程跑一次 randomUUID 的新会话；Web 由 RPC 带 cwd/workspace 决定并可 adopt 已有存档），以及 Web 独有的导出 ZIP 与两个 Web 专属存储域。

## 四、循环在哪里判定停止

停止判定分三层。step 层产生结束理由：模型不再调工具（completed）、输出达 token 上限（max-tokens，且在 turn 内 sticky）、工具宣告终结本轮（concludesTurn）、请求失败且无人要求重试（error）。turn 层在「本步已有结束理由且 inbox.nextStep 为空」时先 serial 派发 agent/turn-stopping 再 break，turn 收尾按 inbox 是否还有 pending 决定 return true/false，驱动器据此停转。此外还有取消（user / parent / hook / disposed 四种原因）、pre-step 被 reject（blocked）、以及 agent-loop 之外的 goal 轮次上限与 ralph 脚本轮次上限。差异在于停机的外缘：headless 有进程级停机与退出码（按最后一个 turn/end 的 reason 决定 0 或 1），Web 没有进程级停机、会话停在 idle 等下一次输入，但多出一条 RPC 取消面。
